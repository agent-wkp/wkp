# ADR-0012: Pluggable pod orchestrator (podman today, Kubernetes later)

Status: accepted
Date: 2026-09-11
Design sections affected: 8.1, 8.2, 8.3
Depends on: ADR-0009 (pod-per-tenant isolation, "must work the same way under Kubernetes later, without a mechanism change"), ADR-0010 (pod lifecycle and addressing)

## Context

ADR-0009 rejected `podman exec` as the front door's mechanism for reaching a tenant's pod specifically because it has no Kubernetes equivalent a running service can call on its hot path, and required whatever mechanism replaced it to "work identically whether the hub runs as podman pods on a single host or as pods in a Kubernetes cluster later, without a rewrite." That requirement was satisfied for git *traffic*: `proxy_to_tenant_pod` (`crates/wkp-hub/src/http.rs`) only ever opens a plain network connection to a tenant pod's own `git http-backend`, which is identical under either runtime.

It was not satisfied for pod *lifecycle*. `crates/wkp-hub/src/tenant_pod.rs`'s `start_pod`/`stop_pod` -- called directly from `handle_git_http`'s on-demand cold-start path (`http.rs`), the `start-pod`/`stop-pod`/`reap-idle-pods` CLI subcommands (`main.rs`), and the idle reaper (`reap_idle`) -- call `Command::new("podman")` directly, with no seam a Kubernetes backend could occupy later without touching every one of those call sites. This surfaced concretely while wiring M5-13's mTLS integration test into CI (#126): the front-door container image (`deploy/hub/Containerfile`) has no `podman` binary at all, so `handle_git_http`'s on-demand pod-start -- the *primary* production code path a tenant's first request after an idle-reap takes -- fails with `ENOENT` inside that container, not just in the test. Fixing that requires deciding how the front-door process reaches a container-runtime control plane at all, which is exactly the question ADR-0009/0010 left open ("How `wkp-hub tenant create` grows from 'make a directory' to 'start a pod'" -- ADR-0009's own follow-up note).

## Options

1. **Fix the container image (install `podman`/`podman-remote`, mount the host's socket) and leave `tenant_pod.rs`'s call sites unabstracted.** Cheapest fix for the immediate CI failure. Rejected as the only change: leaves the exact gap ADR-0009 flagged -- a Kubernetes deployment would need to rewrite `handle_git_http`, `main.rs`'s three pod subcommands, and the reaper, instead of adding one new implementation behind an existing seam.
2. **A `PodOrchestrator` trait in `wkp-hub`, with a `PodmanOrchestrator` implementation now and a reserved (not yet implemented) Kubernetes variant.** Every existing call site depends on the trait, not on `Command::new("podman")` directly. The concrete backend is chosen once at process start (`WKP_HUB_POD_ORCHESTRATOR` env var, default `podman`) and threaded through as a `Box<dyn PodOrchestrator>` / `Arc<dyn PodOrchestrator>`. Selecting `kubernetes` today is a clear startup error, not a silent no-op or a half-built stub -- there is no Kubernetes client code in this repo yet, and CLAUDE.md's "no half-finished implementations" rule means the seam should exist without a fake implementation behind it. Chosen: this is the direct fix for the gap in Context, costs one trait and one call-site threading pass, and does not require writing any Kubernetes-facing code today.
3. **A separate helper binary (`wkp-hub-orchestrator`) that `wkp-hub` shells out to, itself dispatching to `podman` or a Kubernetes client depending on its own environment.** Same pluggability as option 2, but adds a second binary, a second process boundary, and a serialization format between them for no benefit over an in-process trait -- `wkp-hub` is already the "small tool" in question (`start-pod`/`stop-pod` are already its own subcommands); wrapping it in another process just to switch on an env var it could read itself is unjustified indirection. Rejected on CLAUDE.md's "slim core" priority.
4. **Out-of-process orchestration: an external controller (a real Kubernetes operator, or a script) provisions pods and `wkp-hub` only ever proxies traffic, never starts anything itself.** Removes the lifecycle problem from `wkp-hub` entirely. Rejected for this milestone: ADR-0010 already decided the front door itself owns the on-demand cold-start/idle-reap policy (design section 8.2's "micro-SaaS scale" framing -- most tenants inactive most of the time, so lifecycle needs to react to traffic, not run on an external operator's own schedule). Revisiting that split is a larger design change than this ADR's scope.

## Decision

**Introduce `PodOrchestrator`, a trait in `crates/wkp-hub/src/tenant_pod.rs` capturing exactly the two operations every call site needs (`start_pod`, `stop_pod`), with one implementation today (`PodmanOrchestrator`, the existing `Command::new("podman")` logic, unchanged in substance) and a reserved name for a future Kubernetes implementation.** Option 2. `tenant_pod::orchestrator()` selects the implementation from `WKP_HUB_POD_ORCHESTRATOR` (default `"podman"`); `"kubernetes"` is recognized as a reserved, not-yet-implemented value (a clear startup error, matching CLAUDE.md's stance against half-finished implementations) rather than either silently falling back to podman or exposing a hidden second flag with no real backend.

`handle_git_http`, the `start-pod`/`stop-pod`/`reap-idle-pods` CLI subcommands, and `reap_idle` all take `&dyn PodOrchestrator` (or hold one behind an `Arc` in `FrontDoorState`, resolved once at server start) instead of calling `tenant_pod::start_pod`/`stop_pod` as free functions.

**Separately, and regardless of this abstraction:** `deploy/hub/Containerfile`'s runtime stage needs an actual way to reach a podman engine (installing `podman-remote` and bind-mounting the CI/host's rootless podman socket, `CONTAINER_HOST` pointed at it) for the `PodmanOrchestrator` backend to work when `wkp-hub serve` runs inside that container at all -- the trait doesn't change what the concrete podman backend needs to actually execute successfully, only where a second backend could later be added. That deployment fix is tracked as its own follow-up alongside this ADR's code change, not decided here in detail (mount path, socket activation, and any additional container capabilities are implementation specifics for that PR).

**Not decided here:** the actual Kubernetes implementation (client library choice, authentication to the cluster's API server, RBAC scope) -- reserved as a name, not designed. Per-tenant resource/cgroup quotas under either backend remain #110/M5-7's own open design-pass item, untouched by this ADR.

## 2026-09-20 addendum: the Kubernetes implementation (issue #141)

**What was actually decided**, resolving this ADR's own "not decided here" line above:

- **`kubectl`, not a Kubernetes client crate.** Issue #141 originally scoped this as needing "a Rust Kubernetes client crate ... its own `cargo deny`/`cargo vet` justification." Building `KubernetesOrchestrator` (`crates/wkp-hub/src/k8s_orchestrator.rs`) showed that wasn't necessary: `PodOrchestrator`'s two methods are small enough to implement by shelling out and checking exit status, exactly like `PodmanOrchestrator` already does -- `kubectl` is as mature and audited a tool as `podman` itself. No new Cargo dependency, no supply-chain review for a client library.
- **Authentication: a generated in-cluster kubeconfig using `tokenFile`, not a literal token flag.** Unlike a Kubernetes client library, plain `kubectl` does not auto-discover in-cluster credentials (`rest.InClusterConfig()` is client-go's own convenience). `KubernetesOrchestrator::new()` writes a kubeconfig once, at construction, whose user stanza points `tokenFile` at the ServiceAccount's projected token path -- `kubectl` re-reads that file on every invocation, so token rotation is handled for free with no code here tracking token lifetime. RBAC scope: a namespaced `Role` (not `ClusterRole`) granting `get`/`list`/`watch`/`create`/`delete` on `pods`, `services`, `persistentvolumeclaims` -- least privilege, matching this ADR's original framing, not cluster-admin.
- **Storage: one `PersistentVolumeClaim` per tenant, created once, never deleted by this orchestrator.** Rejected `hostPath` (ties a tenant to one node, no multi-node story) and a single shared PVC (loses the per-tenant filesystem isolation ADR-0014 already established). `stop_pod` deletes the `Pod`/`Service` only -- mirrors the podman backend's own "stop the container, keep the bind-mounted data" behavior.
- **A bare `Pod`, not a `Deployment`.** A `Deployment`'s controller would reconcile the Pod back into existence the moment `stop_pod` deletes it, silently defeating idle-reap (M5-7). A bare Pod with the default `restartPolicy: Always` still gets kubelet's own crash-restart for free, so nothing is lost relative to a `Deployment` for the crash-recovery case, while this orchestrator's own start/stop calls stay the sole authority over whether the Pod exists.
- **Addressing confirmed portable, unchanged.** A Kubernetes `Service` named after the tenant slug resolves via ordinary intra-namespace DNS, so `http.rs`'s `proxy_to_tenant_pod` (`http://{tenant_slug}:{port}/...`) needed no code change -- confirming this ADR's original claim that the traffic-proxying half was already runtime-agnostic.
- **`--network none` has no Kubernetes equivalent (no per-container network-namespace opt-out in the Pod API); the seccomp profile is the whole mechanism on this backend**, applied via `securityContext.seccompProfile.localhostProfile` on the `index-worker` container. That profile file must exist on whatever node the Pod is scheduled to -- staged cluster-wide, once, by `deploy/hub/k8s/seccomp-daemonset.yaml`, not by the orchestrator itself.

**Verification:** unit tests in `k8s_orchestrator.rs` cover manifest generation and kubeconfig rendering without a real cluster. `deploy/hub/test-kubernetes-pod-lifecycle.sh` is the real end-to-end proof (start a tenant pod, confirm it answers, stop it) -- written to run by hand against a real cluster, not wired into CI in this change (CLAUDE.md: workflow edits and feature code don't land in the same PR). Run once by hand against a real OpenShift cluster (`wbos.podzone.org`) as part of landing this addendum; see that script's own header for exactly what it checked.

## 2026-09-21 addendum: correcting the network-isolation and storage design

The 2026-09-20 addendum's seccomp-profile and per-tenant-PVC choices were both built, deployed, and tested against a real OpenShift cluster (`wbos.podzone.org`, `paperless-ink/infra`) -- and both turned out to be wrong, not just unconfirmed. This addendum replaces them; it does not touch this ADR's earlier decisions about `kubectl`, `tokenFile` authentication, or bare `Pod`s vs. `Deployment`s, which held up.

**Network isolation: a per-tenant `NetworkPolicy`, not a seccomp profile staged by a cluster-wide DaemonSet.** The seccomp approach's cost was invisible on paper and large in practice: every default/restricted SCC OpenShift ships rejects `hostPath` outright, so staging the profile file onto every node required a dedicated ServiceAccount granted `hostmount-anyuid`, and OpenShift's SCC admission evaluating the *caller* (not just the Pod being created) meant the front door's own ServiceAccount additionally needed a second custom SCC just to reference that profile. All of that privilege existed only to get one file onto every node -- a real, structural requirement of `securityContext.seccompProfile.localhostProfile`, not a configuration mistake, but a bad trade for what it bought. OVN-Kubernetes (this cluster's CNI, and OpenShift's default) fully enforces standard `NetworkPolicy` -- confirmed against the real cluster before committing to this replacement, the same way the seccomp approach's actual cost was confirmed by building it rather than assumed. A `NetworkPolicy` denying all egress from the index Pod needs no cluster-wide staging and no SCC dimension at all (it's a plain namespaced object any ServiceAccount with `create`/`delete` on it can manage), at the cost of the index-worker now having to be its own Pod (next point) rather than a second container sharing the seccomp-hardened one.

**This forces two Pods per tenant, not one Pod with two containers.** A `NetworkPolicy` selects Pods by label; it cannot scope a rule to one container within a shared Pod, and the Kubernetes Pod API has no per-container network-namespace opt-out either (the same gap the 2026-09-20 addendum already noted `--network none` had no equivalent for). `index-worker` gaining real, mechanism-backed network isolation on this backend costs a second scheduled Pod per tenant, in exchange for removing the DaemonSet/hostPath/dual-SCC machinery entirely.

**Storage: one namespace-wide RWX `PersistentVolumeClaim`, `subPath`-isolated per tenant, not one PVC per tenant.** The per-tenant-PVC decision was reasoned correctly for a *single-Pod* tenant, where the isolation is trivial by construction. It stops working once `index-worker` is a second, separate Pod needing concurrent access to the same tenant data as `serve`: this cluster's only StorageClass (`lvms-vg1`, topolvm) is `ReadWriteOnce`-only, so two Pods sharing one tenant's data need `ReadWriteMany` -- and a fresh RWX `PersistentVolume` per tenant would mean running a real NFS (or equivalent) server *per tenant*, dramatically more infrastructure than one shared server multiplexing every tenant behind `subPath`. `paperless-ink/infra`'s `manifests/70-shared-tenant-storage.yaml` provides that one shared PVC, backed by a pure-Rust NFS server (`containers/nfs-server/` in that repo) chosen there for a parallel reason to this ADR's own network-isolation story: the mainstream alternatives (kernel `nfsd`, NFS-Ganesha) both needed root or `CAP_SYS_ADMIN`-class privilege for reasons specific to their implementations, where a server that never impersonates a connecting client's identity needs neither -- see that repo's `containers/nfs-server/README.md` for the full investigation. Each tenant's isolation now comes from `subPath: <tenant_slug>` in both Pods' volume mounts (an init container `mkdir -p`s the subdirectory against the unscoped mount first, since `subPath` targets aren't guaranteed to be auto-created), not from owning a distinct PV; `stop_pod` still never touches this PVC, unchanged from the prior addendum, since it's shared namespace-wide rather than any one tenant's to delete.

**RBAC gains one verb**: `networkpolicies` (`create`/`delete`/`get`), alongside the `pods`/`services`/`persistentvolumeclaims` the 2026-09-20 addendum already granted. `persistentvolumeclaims` access is retained even though this orchestrator no longer creates one per tenant -- `kubectl apply`'s dry-run/diff step still reads the (now shared, pre-existing) PVC's manifest as part of applying the Pod specs that reference it.

**Consequences for the earlier addendum's own claims:** its "Storage" and "`--network none` has no Kubernetes equivalent" bullets are superseded by this one, not merely extended -- `deploy/hub/k8s/seccomp-daemonset.yaml` and `deploy/hub/k8s/tenant-pod-scc.yaml` are deleted, not kept as an alternate path. Its `kubectl`, `tokenFile`, and bare-`Pod` decisions are unaffected.

## Consequences

- `tenant_pod.rs`'s public surface changes from two free functions (`start_pod`, `stop_pod`) plus `reap_idle` to a trait, one concrete implementation, and a selector function; every caller (`main.rs`, `http.rs`, `front_door.rs`) threads a `&dyn PodOrchestrator` instead of calling the module directly. This is a larger diff than the container-only fix (option 1) but touches only call sites already coupled to `tenant_pod`, not new surface elsewhere.
- Selecting `WKP_HUB_POD_ORCHESTRATOR=kubernetes` today fails fast at startup with a clear message, rather than pretending to work. A future PR implementing the Kubernetes backend removes that error path by giving it a real implementation -- it does not need to touch `handle_git_http`, the CLI subcommands, or the reaper again.
- The concrete container-socket-access fix for the `podman` backend (installing `podman-remote`, mounting a socket) is deploy-surface, CODEOWNERS-gated per CLAUDE.md, same as any other `deploy/` change -- tracked and reviewed as its own PR, not folded into this ADR's trait-introduction change.
- No behavior change for the existing single-host podman deployment this milestone targets: `PodmanOrchestrator`'s methods are the prior `start_pod`/`stop_pod` logic, unmodified in substance, just reachable through the trait instead of directly.
